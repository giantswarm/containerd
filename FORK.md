# The Giant Swarm line of containerd

This repository is Team Bumblebee's fork of [containerd/containerd](https://github.com/containerd/containerd): the
containerd that [giantswarm/vm-manager](https://github.com/giantswarm/vm-manager)'s node images run, built from an
upstream release ("the pin") plus the changes the line carries, and published to gsoci. It answers one question from
one place: **which containerd do the nodes run, and why does it differ from upstream?**

**Why the line exists.** The nodes enforce IPE: code executes only from a dm-verity device whose root-hash signature
the kernel trusts (`dm_verity.require_signatures=1`). containerd's EROFS snapshotter sets up dm-verity for each layer
since 2.3.0, but computes the root hash on the node and passes no signature, so no layer mounts. Per-layer root-hash
signatures, fetched as OCI referrers, are the first milestone of the RFC
[containerd/containerd#12081](https://github.com/containerd/containerd/issues/12081); no release implements them. The
line carries that change as one upstream-ready commit until a containerd release contains it; the nodes then return
to the distribution's containerd and the line is retired.

## Branches

| Branch | What it is | Who moves it |
|---|---|---|
| `main` | A pure mirror of upstream `main`, fast-forwarded daily. Never edited, never the target of a pull request. The mirrored commits carry upstream's workflow files, whose runs the sync cancels right after its push. | the `sync-upstream` workflow (as the HeraldBot App); a repair is a `workflow_dispatch` of it |
| `giantswarm` (default) | **The line**: the pin + the carried patches + this fork's own files. Every change is a pull request against it. A carried patch is **rebase-merged**, one upstream-ready commit per patch, so its patch identity survives and a re-pin's `git rebase` drops it by itself once the pin contains it; fork-infrastructure pull requests (this file, CI, workflows) are **squash-merged**. | pull requests; a re-pin (below) |
| `fork/<topic>` | pull-request branches against `giantswarm` | the team |
| `upstream/<slug>` | an upstream-ready change, based on the mirror's `main`, prepared for upstream ("Contributing") | the team |
| `sync/<date>-<pin>` | a re-pin candidate: the new pin + the replayed commits of the line | the person re-pinning |

## Pin

**`v2.4.2`** (upstream commit `b7a25261e029d68978bbf290df0a62fc819b3c51`), the release the distributions ship today.
The pin is the version upstream's tree states for itself (`version/version.go`, `Version = "2.4.2+unknown"`), so the
build, the release tags and the artifact's `io.giantswarm.upstream.version` annotation read it from the tree
(`.github/scripts/line-version.sh pin`); nothing else records it.

## Carried patches

Everything on `giantswarm` that is neither in the pin nor the fork's own infrastructure has a ledger file of its own in
[`fork/`](fork/) (format in [`fork/README.md`](fork/README.md)); the directory is the index.

The fork's own infrastructure, ours to keep and never sent upstream:

- `FORK.md`, `fork/`, `renovate.json5` (Renovate off: dependencies move with the pin).
- `.circleci/config.yml`: hand-written, declared here as the line's pipeline; nothing on the line is generated by
  devctl ("Publishing").
- `.github/scripts/line-version.sh`, `.github/workflows/tag-release.yaml` ("Releases"),
  `.github/workflows/sync-upstream.yaml` ("Branches").
- Upstream's workflows that publish, need upstream's secrets or run on a schedule are **removed** on this branch:
  `release.yml` with `release/`, `api-release.yml`, `images.yml`, `build-test-images.yml`, `nightly.yml`, `links.yml`,
  `stale.yml`, `scorecards.yml`, the four `windows-*periodic*` workflows, and `.github/dependabot.yml`. Nothing
  publishes from GitHub Actions. The others stay as upstream has them and trigger on upstream's branches only.

## Re-pin

A re-pin moves the line to a newer upstream release, e.g. when a release carries a patch the line holds:

1. Cut `sync/<date>-<new pin>` from the new tag and replay the line onto it:
   `git rebase --onto <new pin> <old pin> giantswarm` on a copy of the line. A carried patch the new pin contains
   drops out by itself; its ledger file moves to `status: dropped` with the release that contains it.
2. Open a pull request of the candidate against `giantswarm` for review and CircleCI's build (closed, never merged:
   a merge cannot rewrite the line).
3. A maintainer with the ruleset's bypass lands exactly the reviewed commit on `giantswarm` with a force push. The
   push releases `v<new pin>-gs.1`; the revision counter starts again for every pin.

## Releases

Every push to `giantswarm` is a release: the `tag-release` workflow puts the next tag **`v<pin>-gs.<N>`**
(`v2.4.2-gs.1`, `v2.4.2-gs.2`, …) and its GitHub Release on the pushed commit; `N` counts the releases of that pin. A
merged carried patch therefore ships as the next revision of the pin; a re-pin starts at `-gs.1`.

- **Where a release comes from**: a commit of `giantswarm`, nothing else. The publish job checks that the tagged
  commit is an ancestor of `giantswarm` and fails naming the tag and the commit otherwise.
- **Who tags**: `tag-release` alone, as GitHub Actions on a push to `giantswarm`. Nobody pushes a `v*-gs.*` tag by
  hand, and upstream's `v*` tags are not mirrored here. No ruleset enforces this yet: the repository's declaration in
  giantswarm/github cannot express a tag ruleset, so the provenance check above is the guard.

## Publishing

CircleCI builds `containerd`, `containerd-shim-runc-v2` and `ctr` for **linux/amd64** as static binaries with
containerd's own Makefile (`make STATIC=1 VERSION=<version> REVISION=<commit>`, upstream's Go for the pin, vendored
modules) and pushes them to gsoci, signed with the organisation's CircleCI identity (cosign):

| | |
|---|---|
| Repository | `gsoci.azurecr.io/giantswarm/containerd` |
| Tag | `v<pin>-gs.<N>`, the git tag itself (`v2.4.2-gs.1`), pushed only by the tag's own build as exactly `CIRCLE_TAG`; releases only, no dev builds |
| Manifest | OCI image manifest, `artifactType` `application/vnd.giantswarm.containerd.binaries.v1`, empty config |
| Layer | one, `application/vnd.oci.image.layer.v1.tar+gzip`, titled `containerd-linux-amd64.tar.gz`: `bin/containerd`, `bin/containerd-shim-runc-v2`, `bin/ctr` (owner 0:0, mtime the commit's) |
| Annotations | `org.opencontainers.image.version`, `.revision`, `.source`; `io.giantswarm.upstream.version` (the pin); `io.giantswarm.platform` (`linux/amd64`) |

```sh
oras pull gsoci.azurecr.io/giantswarm/containerd:v2.4.2-gs.1      # writes containerd-linux-amd64.tar.gz
tar -xzf containerd-linux-amd64.tar.gz                             # bin/containerd, bin/containerd-shim-runc-v2, bin/ctr
bin/containerd --version                                           # containerd github.com/containerd/containerd/v2 v2.4.2-gs.1 <commit>
```

**Published tags are immutable.** The publish job takes the tag from CircleCI's own `CIRCLE_TAG`, checks that the
binaries were built under it, and refuses a tag that already exists in gsoci; what it pushes is what it signs
(`<repository>@<digest>`). A release is never re-published: a fix is the next revision.

**Branches never publish.** A push to a branch runs the build alone; only the release tag's `publish-release` job gets
the `architect` context with the registry credentials and the signing identity. The pipeline is triggered by pushes
to this repository only, so a pull request from a fork never builds here.

gsoci is the only registry: nothing of the line is published to ghcr.io or as a GitHub Release asset.

## Contributing

- **Upstream first, prepared here.** Every behavioural change is prepared for upstream as one upstream-ready commit:
  upstream's conventions and tests, DCO-signed (`git commit -s`), no Giant Swarm references. It is pushed as an
  `upstream/<slug>` branch on this repository, based on the mirror's `main`, and lands on the line as its own pull
  request with its ledger file in `fork/`. Its ledger file reads "to file — prepared in the fork: branch
  `upstream/<slug>`" until the upstream pull request is opened, and links it from then on. A change to a carried
  patch lands as a commit of its own, listed in the patch's ledger file next to it (a rebase merge refuses `amend!`
  and `fixup!` commits); its `upstream/<slug>` branch gets the patch with the change folded in. A human reviews the
  prepared branches in batches, decides what goes upstream and opens it; an agent never opens, comments on, reviews
  or closes a pull request or issue on the upstream repository.
- **Public only.** This repository is public: a ledger file, a commit message and this file cite public issues and
  pull requests only, and where reasoning lives in a private tracker it is written out here instead.
- **Merge methods**: a carried patch is rebase-merged (one commit per patch); fork-infrastructure changes are
  squash-merged with a Conventional Commits title. Every merge is a release ("Releases").
- **Builds**: `make STATIC=1 bin/containerd bin/containerd-shim-runc-v2 bin/ctr` builds what the line publishes;
  CircleCI builds every branch's push and publishes nothing from it. A change is proven on a node with a local build
  before it merges.
- **Dependencies** move with the pin: Renovate and Dependabot are off on the line.
